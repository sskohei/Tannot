# アーキテクチャ

```text
Browser
  ├─ Next.js UI
  └─ Better Auth session
          │
Cloudflare Workers
  └─ Hono API
      ├─ Auth / ownership checks
      ├─ Dictionary & example service
      ├─ Audio service (Kokoroへのオンデマンド中継)
      ├─ Stripe service / webhook
      └─ D1 repository
```

## 単語帳作成フロー

入力を検証・正規化し、EJDict で訳を検索する。Tatoeba は入力語を含む英語例文から候補を選び、出典 ID と作者情報を保持する。単語帳作成時には音声を生成せず、学習画面で再生要求を受けたときだけ、認証済みWorkerがKokoro推論サービスへテキストを渡し、音声バイナリをブラウザへ中継する。音声生成が失敗しても、テキストカードと学習機能は利用可能にする。

音声本体、object key、固定URL、生成状態はD1やオブジェクトストレージに保存しない。再生APIはカードの所有権を確認し、単語または例文のテキストをKokoroサービスへ渡す。推論サービスのURLや認証情報はWorkerの環境変数・secretだけで管理し、ブラウザには公開しない。

データソースはアプリのリクエストごとに外部取得するのではなく、利用条件を確認した上でインポートした検索用データを優先する。元データの更新日とインポート手順を記録する。

## 境界

- Next.js: 表示、入力、音声再生、API 呼び出し。
- Hono: 認証済みリクエストの検証、所有権確認、業務処理、D1 アクセス。
- D1: ユーザー、単語帳、カード、学習履歴、サブスクリプション状態。
- Kokoro推論サービス: 再生要求ごとに音声を生成し、`audio/mpeg` などの音声レスポンスを返す。Kokoro-82Mの推論はWorkers内ではなく、対応する外部基盤で実行する。

## 音声の保存・配信方針

- 音声は再生要求時に生成し、Workerからブラウザへ直接中継する。R2などの永続ストレージは使用しない。
- 音声APIはカードIDと音声種別を受け取り、ログインユーザーの単語帳に属するカードだけを再生できるようにする。任意テキストを未認証で合成できるAPIは公開しない。
- レスポンスは原則 `Cache-Control: private, no-store` とし、音声を保存しない仕様を明確にする。ブラウザの一時的な再生バッファは許容する。
- Workersのメモリ・CPU制約を考慮し、Kokoroの推論はWorkers内で実行せず、外部のKokoro推論サービスへ委譲する。
- 同じ音声の再生が多くなった場合のキャッシュや事前生成は、将来の別仕様として検討する。

基本構成は「音声テキストはD1のカードから取得、推論は外部Kokoro、配信はWorkerから直接中継」とする。
